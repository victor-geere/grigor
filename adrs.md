Architectural Decision Records for the Grigor Language

-----------------------------------------------------------
ADR-001: Choice of Core Type Theory
Status: Accepted
Date: 2025-05-26
Author: Grigor Core Team

Context:
Grigor is a fully explicit proof language where every proof is a concrete lambda-term and must be mechanically checkable without external automation. The underlying type theory defines the logical power, consistency, and complexity of the type checker.

Decision:
Adopt the Calculus of Inductive Constructions (CIC) with:
- Dependent products (forall) and dependent functions (fun).
- Cumulative universe hierarchy: Prop <= Set <= Type(0) <= Type(1) <= ...
- Strictly positive inductive families with dependent elimination (match ... return).
- Structural recursion (fix) and co-recursion (cofix).
- Internal identity type eq with J eliminator.
- Definitional equality given by beta, iota, delta, eta reduction.

Options considered:
1. First-order logic – too weak for higher-order modularisation.
2. Martin-Löf Type Theory without universes – no built-in universe hierarchy, making large constructions awkward.
3. CoC without inductive types – data must be Church-encoded, poor computational behaviour.
4. Homotopy Type Theory – univalence and higher inductive types add enormous kernel complexity, unnecessary for a minimal proof language.

Consequences:
Positive: Can formalise nearly all constructive mathematics; well-understood meta-theory; modularity via functors possible.
Negative: Dependent pattern matching is verbose; universe subtyping adds checker complexity; fully explicit terms are longer (intentional).

ADR-002: ASCII-Only Syntax
Status: Accepted
Date: 2025-05-26
Author: Grigor Core Team

Context:
Grigor aims to be maximally accessible and implementable on any system without special fonts or input methods. The concrete syntax must use only characters from the printable US-101 keyboard.

Decision:
The entire language is restricted to ASCII characters:
- Keywords: forall, fun, match, with, end, as, in, return, etc.
- Arrow -> for non-dependent product; /\ and \/ for logical connectives (user-defined).
- := for definitions, . for termination.
- No Unicode symbols (no forall, lambda, arrow, and, or, not-equal, less-than-or-equal).

Consequences:
Positive: Portability; no ambiguity from Unicode; easy to write and read on any terminal.
Negative: Verbosity (e.g., forall instead of universal quantifier symbol); some mathematicians may find it less aesthetic, but clarity is prioritised.

ADR-003: No Tactics or Proof Automation
Status: Accepted
Date: 2025-05-26
Author: Grigor Core Team

Context:
Many proof assistants provide tactic languages to construct proof terms interactively. Grigor's philosophy is that every proof must be a fully explicit term, written by the user or generated by an external program, but never constructed by an opaque internal automation.

Decision:
Grigor has no tactic language. Proofs are ordinary terms of the language. The type checker verifies these terms directly; it never attempts to fill in missing sub-proofs, perform automatic rewriting, or apply heuristics. Axioms and theorems are introduced with explicit proof terms (or Axiom for admitted statements).

Consequences:
Positive: Absolute transparency – a proof is exactly what is written; no hidden steps. The kernel stays small and auditable.
Negative: Writing large proofs by hand is extremely laborious. External tooling may be needed for practical use. This is an accepted trade-off for a minimal, rigorous core.

ADR-004: Module System with Functors
Status: Accepted
Date: 2025-05-26
Author: Grigor Core Team

Context:
To support modular development and reuse, Grigor needs a way to group definitions and parameterise them over other modules.

Decision:
Adopt a module system inspired by OCaml and Coq:
- Module declarations can contain any top-level items.
- Module Types describe signatures; they are structural.
- Functors are parameterised modules.
- Include copies all definitions of a module into another.
- Import brings names into scope without the module prefix.
- with constraints allow refinements of signatures.

Consequences:
Positive: Enables large-scale structured developments. Functors allow generic algorithms.
Negative: Module elaboration adds a layer of complexity before the core type checker runs. The kernel need not understand modules, only the elaborated terms.

ADR-005: Built-in Identity Type with J Eliminator
Status: Accepted
Date: 2025-05-26
Author: Grigor Core Team

Context:
Equality is fundamental for rewriting and reasoning. A precise, well-behaved notion of equality that fits with dependent types is required.

Decision:
Include a single built-in inductive family eq:
Inductive eq (A:Type) (x:A) : A -> Prop := refl : eq A x x.
Its eliminator J is provided as a primitive constant:
J : forall (A:Type) (x:A) (P:forall y, eq A x y -> Prop), P x (refl A x) -> forall (y:A) (e:eq A x y), P y e
No other equality axioms (K, UIP, univalence) are built-in. The reduction rule J ... refl ... reduces definitionally.

Consequences:
Positive: Minimal, standard, consistent with CIC. Definitional computation for refl simplifies proofs.
Negative: Many equality proofs become long without tactic automation. No extensionality beyond what can be derived from J.

ADR-006: Universe Hierarchy and Cumulativity
Status: Accepted
Date: 2025-05-26
Author: Grigor Core Team

Context:
To avoid paradoxes and support large constructions, Grigor requires a universe hierarchy.

Decision:
Universes are:
- Prop (impredicative, for propositions)
- Set (predicative, small datatypes)
- Type(i) (predicative, large types)
Cumulativity: Prop <= Set <= Type(0) <= Type(1) <= ...
Subtyping is used silently: a term of type A : Type(i) can be used where Type(j) with i <= j is expected.

Consequences:
Positive: Avoids Girard's paradox; natural for typical usage. Cumulative subtyping reduces bureaucratic lifting.
Negative: Subtyping adds a modest overhead to the checker, but it's well-understood. The hierarchy is unbounded, requiring level variables.

ADR-007: Fully Explicit Terms (No Implicit Arguments)
Status: Accepted
Date: 2025-05-26
Author: Grigor Core Team

Context:
Many dependently-typed languages allow implicit arguments filled by unification, obscuring the proof term.

Decision:
Grigor requires every argument to be supplied explicitly. There is no implicit argument mechanism. Syntax { x } is reserved but currently ignored; all binders are explicit.

Consequences:
Positive: The proof term is a complete, self-contained witness; no hidden parameters. The checker is simpler and more predictable.
Negative: Terms become more verbose (e.g., cons nat 3 (cons nat 2 (nil nat)) instead of cons 3 (cons 2 nil)). Accepted cost for absolute clarity.

ADR-008: Reference Implementation in Python
Status: Accepted
Date: 2025-05-26
Author: Grigor Core Team

Context:
To demonstrate the language and provide a practical checker, a reference implementation is needed. It should be readable and easy to modify.

Decision:
The reference type checker is written in Python 3.10+, using the Lark parsing library. The core reduction engine and type checker are in pure Python, following the typing rules directly.

Consequences:
Positive: Python is widely understood; code serves as executable specification. Rapid prototyping of language changes is easy.
Negative: Performance is poor compared to native compilers; not suitable for large-scale proofs. A future high-performance kernel could be derived from this reference.
